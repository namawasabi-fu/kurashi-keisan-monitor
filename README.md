# くらしの計算室・監視専用パッケージ

週次のGitHub Actionsでは計算ロジックだけを実行します。共有ランナーからBloggerへのHTTP取得で429が続いたため、クラウド実行から公開サイトへのリクエストをなくしました。Blogger、Search Console、Googleアカウントの認証情報は含みません。Node.js 22 の標準機能のみ使用します。

- ローカルで公開サイト全件と計算ロジックを検査: `node weekly_monitor.mjs`。PCの起動と手動実行が必要です。
- GitHub Actionsと同じ通信なし検査: `node weekly_monitor.mjs --local-only`。公開サイトの稼働・リンク・SEOは検査しません。
- GitHub公開リポジトリのデフォルトブランチにこのフォルダの**中身だけ**を配置すると、ワークフローは毎週月曜02:17 UTCに実行します。
- Actionsの手動実行で初回動作を確認し、通知は本人が「失敗のみ」を選択してください。障害を自動修正しません。
- GitHubの公開リポジトリで標準ランナーは無料。ただし60日間リポジトリの活動がないと予定実行が無効になるため、完全放置はできません。約6週間ごとにGitHub外のカレンダー等で確認日を管理し、Actions一覧の最終成功日時とワークフローの有効状態を確認してください。GitHub停止時にGitHub内通知だけでは検出できません。
- 予定実行が止まると監視自身からは通知できません。停止時は手動で再有効化します。活動偽装の自動コミットは行いません。
- 失敗時の小さなJSONログだけを7日間アーティファクトに保存します。ローカル全件検査の通信失敗は `monitor_transport_error` として記録し、サイトの故障とは断定しません。
- 2026-10-13 のGitHub共有ランナーでは、Bloggerへの一部リクエストがGoogleの制限ページへ転送され429になりました。ローカル全件検査は429を再試行せず `monitor_transport_error` として安全停止します。クラウドからの公開サイト監視は未実施です。アクセス制限の回避やCAPTCHA処理は行いません。
- スケジュールが停止した場合: リポジトリの Actions → Kurashi weekly monitor → Enable workflow を選び、Run workflow で手動実行して結果を確認します。無意味な自動コミットは作りません。
- 個人情報、認証トークン、Bloggerバックアップ、投稿本文をこのリポジトリへ入れないでください。

生成元は作業フォルダの `prepare_monitor_package_v13.mjs`。再生成後はローカル検査を実行してください。
